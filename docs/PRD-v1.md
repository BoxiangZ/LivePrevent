# LivePrevent PRD v1.0 — 多模态居家监测与告警

**状态：** v1 产品需求与验收基线  
**日期：** 2026-10-03  
**适用范围：** 家属端 Web 优先；护理机构仅保留预览，不作为本版本交付承诺。

## 1. 版本目的与现有基线

LivePrevent 帮助家属更早发现居家老人活动、设备状态和基础生理观察中的异常，并通过可解释、可确认、可升级的告警协同处理。

本版本明确采用**多模态输入**：用户可主动提交结构化观察资料（手工输入、CSV、JSON）和可选的短 MP4 视频，系统结合两类证据给出事件推断、风险概率和下一步通用建议。这里的“预测”指对当前或近期风险事件的概率性判断，不是疾病诊断、治疗建议或对未来健康结果的保证。

当前仓库已经提供一个可运行的本地样例工作区：四级风险、样例规则、两阶段跌倒、模拟升级链、事件复核、v3 API、结构化资料和可选 MP4 上传、Kimi 视频观察及 Kimi 文本解释。本 PRD 不把这些样例能力描述为真实设备监测、真实短信/邮件送达、生产身份系统或临床验证结果。P0/P1/P2 是基于现有基线的交付优先级。

## 2. 产品边界

- LivePrevent 是辅助监测和告警工具，不提供医疗诊断，不替代医生判断、紧急服务或 SOS 服务。
- 对外不得承诺“预防”疾病、跌倒或其他事件；风险等级表达的是已知证据下的处理优先级。
- 自动设备路径不持续上传视频，也不提供远程实时查看画面。
- 用户可主动选择上传一次性样例 MP4，用于某次 assessment 的分析；上传前须明确确认用途与授权。连续视频采集不属于本版本范围。
- 资料、视频、模型输出和告警均必须显示来源与不确定性。样例资料、模拟设备状态和模拟通知不得伪装为真实状态或真实送达。

## 3. 用户、角色与成功任务

### 3.1 用户

- 被监测人（Subject）：同意主体，可暂停或撤销监测；无法表达同意时由合法监护人代理。
- 主家属：配置设备、联系人、订阅与权限；可确认和处理告警。
- 其他家属／护理联系人：在授予范围内查看、确认和处理告警。
- 护理机构：本版本仅使用静态或模拟的 Patient Risk Board 预览。

### 3.2 核心任务

1. 家属看到当前状态、数据新鲜度和需要立即处理的事项。
2. 家属提交一组观察数据，可附一段短视频，查看该资料的分析结果、证据、局限和来源。
3. 联系人收到 Critical 告警后确认、复核、结案；未确认时系统按联系人链升级。
4. 被监测人或合法代理能够控制同意、可见范围和暂停状态。

## 4. 统一风险与决策原则

| 等级 | 含义 | 默认行为 |
|---|---|---|
| Stable | 已有证据与个人基线一致 | Dashboard 展示，不通知 |
| Watch | 轻度偏离、证据有限或已恢复 | Dashboard 展示；可选邮件 |
| Important | 明显偏离，建议尽快联系确认 | Dashboard、Email、Push；SMS 可选 |
| Critical | 可能需要立即处理 | 持续红色状态、多通道通知和升级链 |

- 风险等级的唯一裁决者是版本化、可审计的 Decision Engine；模型不能直接改变等级。
- 模型可输出观察证据、置信度和概率建议。Decision Engine 必须保存使用的规则版本、阈值、输入证据和最终理由。
- 低置信度、冲突信号、设备离线、覆盖范围外或超出时间窗的资料必须降级为 Watch 或 Unknown，并说明数据不足，不能直接升为 Important/Critical。
- 任何 Critical 都不能只依赖 Email。

## 5. 多模态输入、推断与预测

### 5.1 支持的输入

| 输入 | 用途 | 当前样例基线 |
|---|---|---|
| 手工观察 | 补充单项事实，如冲击、是否佩戴、睡眠、恢复活动 | 已实现 |
| CSV / JSON | 一次性导入结构化观察 | 已实现；最多 3 个文件、1,000 条观察 |
| 短 MP4 | 提取可见运动、跌倒姿态、恢复或不确定证据 | 已实现为可选私有上传；最大 50 MiB、120 秒 |
| 自动手表／摄像头 | 持续活动、健康与设备心跳 | 仅样例状态；真实接入为 P1 |

### 5.2 多模态分析流程

```text
结构化观察 + 可选视频
        ↓
格式、时间窗、覆盖范围和同意校验
        ↓
视频观察提取（Kimi） + 结构化证据标准化
        ↓
证据一致性／冲突／缺失评估
        ↓
概率建议与可追溯证据
        ↓
版本化 Decision Engine（最终等级、是否告警、渠道）
        ↓
模板通知（不等待模型） + 可解释的结果页
```

### 5.3 推断和预测要求

- 系统可推断：疑似跌倒、恢复活动、长时间无活动、心率偏离、活动下降、设备数据缺口和一般性检查结果。
- 视频模型只描述片段内可见动作；不得识别人物、从画面推断生命体征、根据音频/画面文字执行指令，或推断片段外发生的事情。
- 输入资料的发生时间、五分钟选择窗和摄像头覆盖范围是规则裁决的必要上下文。历史上传视频末尾未观察到恢复，不得自动升级为 Critical。
- 最终结果至少显示：风险等级或 Unknown、标题、简明摘要、支持与排除的证据、局限、建议的通用动作、模型是否使用及回退原因、决策引擎和规则版本。
- 无模型密钥、模型失败、超时或输出不合法时，必须返回部分结果或规则模板，并清楚标示“模型未用于本次结果”。
- 发送给第三方模型前应只发送本次分析必要的数据。对于用户主动上传视频，确认文案必须写明视频会传给 Kimi 作观察提取；自动设备路径不得将连续视频上传给模型。

### 5.4 验收标准

- 结构化资料可单独完成分析；结构化资料加视频可完成合并分析。
- 视频失败不会阻塞结构化规则结果；结果为 `partial` 并列出原因。
- 冲突、超出时间窗、覆盖范围外、无证据都不能显示为 Stable。
- 同一提交幂等；取消、重试、删除视频和切换被监测人不会串改结果或越权读取资料。

## 6. 事件、基线与设备规则

### 6.1 基线与冷启动

- 基础指标学习期为 14 天；睡眠和趋势为 28 天。学习中显示 `Learning baseline — day X / N`。
- 学习期启用跌倒、设备离线与保守的极端异常；关闭依赖个人基线的 Important 及趋势提示。
- 基线持续滚动更新，但被标记为异常、设备问题或低质量的样本不得纳入更新；提供受授权人员使用的基线重置和审计入口。

### 6.2 跌倒

1. 发现候选信号时创建 Possible Fall，并进入三分钟恢复观察窗。
2. 有站起或走动等恢复证据时降为 Watch，并记录“疑似跌倒，已恢复活动”。
3. 无恢复且满足 Critical 规则时升级为 Critical。
4. Demo 可以将观察窗加速为十秒，但必须清楚标示为 Demo 时间。

### 6.3 无活动与设备数据缺口

- 无活动判定必须同时考虑睡眠、佩戴、时段个人基线及摄像头覆盖范围。
- 未佩戴或摄像头不在覆盖房间时，不能仅以静止判定无活动异常。
- 单设备离线超过两小时为 Watch；所有数据源离线超过四小时为 Important（Data gap）。
- 离线期间抑制依赖该设备的活动下降和静止告警；Overview 显示最后同步、佩戴、电量、在线状态和不可验证原因。

## 7. 告警、通知与升级（P0）

### 7.1 状态机

`Open → Acknowledged → Resolved`；仅 Watch/Important 可在无新信号后 Auto-expired。Critical 绝不自动结案。

- Acknowledge 记录授权联系人和时间，并停止升级。
- Resolve 必须选择真实事件已处理、误报、设备问题或其他，并可添加备注。
- 每个查看、确认、结案、授权变更、导出和同意变更写入审计日志。

### 7.2 Critical 升级链

| 时点 | 行为 |
|---|---|
| T+0 | 联系人 #1：Email + SMS + Push |
| T+5 分钟 | 未确认：通知 #2，并提醒 #1 |
| T+15 分钟 | 未确认：通知所有联系人 |
| T+30 分钟 | 标为 Unacknowledged；Dashboard 保持 Critical，此后每 15 分钟提醒所有联系人 |

Critical 不受静音时段影响。Important 可遵守各联系人的静音时段，且需在 UI 说明预计发送时间与合并行为。

### 7.3 通知内容与送达

- Email/SMS 仅可包含别名、事件类别、优先级、当地发生时间、登录链接；不得包含心率数值、活动百分比、摄像头姿态、支持信号、诊断性描述或详细建议。
- 所有 Critical Email/SMS 含“如您认为这是紧急情况，请立即联系当地紧急服务。LivePrevent 不是紧急呼叫服务。”
- Critical 链接为一次性、30 分钟有效，打开后必须完成会话验证，并绑定被授权的联系人身份。
- P0 接入真实 Email、SMS 与浏览器 Push 提供商；保存 provider message ID、接受状态、投递状态、失败原因和重试记录。预览或本地模拟消息必须标为 simulated，不能显示为 delivered。

### 7.4 P0 验收标准

- 真实提供商的测试环境可验证三种渠道、失败回执、重试和升级；任意单渠道失败不会阻止其余渠道和升级计时。
- Critical 邮件/SMS 经自动测试校验为最小化内容；完整支持信号只在已登录的事件页展示。
- #2 联系人使用自己的账户和有效一次性链接可确认；其他账户或过期/已使用链接被拒绝。

## 8. 同意、隐私、账户与权限（P0/P1）

### 8.1 同意与暂停（P0）

- Onboarding 记录同意人、时间、身份（本人或合法监护人）、监测设备、数据类别和可见人员。
- 被监测人或合法监护人可撤销或缩小同意范围；撤销后立即停止相应采集与分析，暂停期间不得产生无活动告警。
- 摄像头安装页必须展示覆盖地图、盲区和不建议安装的区域（卧室、浴室），并要求确认设备指示灯和告知标识。

### 8.2 权限与身份（P0）

- 实施独立账户、邀请、角色、人员绑定和服务端授权；不得依靠客户端人员选择器实现权限控制。
- 家属账户提供可实际使用的 2FA；Critical 深度链接必须在登录会话和联系人绑定都有效后才可完成确认。
- 最低权限：主家属可管理联系人/订阅/成员；其他家属按授权查看趋势；护理员按授权查看；事件视频默认仅被监测人和明确授权的主家属可查看。

### 8.3 数据生命周期（P1）

- 原始传感器资料保留 30 天；事件和聚合指标 12 个月；事件视频 7–30 天且用户可缩短；审计日志 24 个月；撤销同意或注销后 30 天内删除，法定保留除外。
- 为每类数据实现可执行的到期删除任务、删除审计和失败告警，而不是只保存保留期常量。
- 本地文件、数据库、备份及模型供应商的数据处理/删除责任必须在隐私政策中分别说明。

## 9. 页面与体验（P1/P2）

### P1：家属端

- Login / Onboarding：账户与 2FA、同意、设备绑定、覆盖地图、联系人链和订阅设置。
- Overview：四级状态、数据新鲜度、基线学习进度、核心指标、最新事件和单一主操作。
- Elder Detail：30/90 天趋势、个人基线、事件时间线、设备状态、证据与局限。
- Alerts：活动/已处理列表、确认、结案、误报或设备问题反馈、通知与审计时间线。
- Assessments：提交资料和视频、分析进度、部分结果、取消/重试、来源、视频删除和事件链接。
- Settings：联系人顺序、时区、渠道、静音时段、权限、隐私、保留期和暂停/撤销入口。

### P2：扩展与运营能力

- Patient Risk Board 继续仅作为模拟预览；不能声称已交付机构多租户能力。
- 在后续独立范围内评估多租户、机构 RBAC、值班升级链、批量导入、EHR 对接和机构级审计导出。
- 引入检测质量、告警疲劳、确认时长、未确认率、设备在线率、基线完成率和模型回退率仪表盘。
- 支持套餐权益的服务端执行：Basic 为 1 位被监测人、30 天趋势、2 个家属账户；Premium 为多位、90 天趋势和可配置成员。所有套餐均不得限制 Critical 多通道告警与升级。

## 10. 实施优先级与完成定义

| 优先级 | 交付内容 | 完成定义 |
|---|---|---|
| P0 | 真实多通道通知、最小化通知模板、独立账户/角色/2FA、会话验证的一次性链接、同意与暂停 | 可在测试环境端到端证明身份、送达、确认、升级、撤销与审计；不再把模拟功能表述为真实能力 |
| P1 | 真实设备接入与离线规则、基线异常排除、静音时段、生命周期删除、完整家属端体验 | 有自动化回归和可观察运行指标；数据质量或设备不可验证时不误显示 Stable |
| P2 | 机构预览深化、套餐执行、运营度量和后续多租户准备 | 与家庭数据和权限隔离；尚未承诺 EHR、电话外呼或完整 B2B 上线 |

## 11. 必测场景

- Stable 且数据新鲜；Stable 但数据过期；暂停；学习期；无数据。
- 跌倒候选、观察窗恢复、无恢复升级、Critical T+5/T+15/T+30、确认停止升级、Critical 人工结案。
- 单设备离线两小时、所有设备离线四小时、未佩戴、睡眠、覆盖范围外、冲突证据。
- 结构化资料单独分析；结构化资料加视频；视频模型失败；Kimi 文本失败；部分结果；取消、重试、幂等与删除视频。
- 联系人静音时段、短信/Push 失败、Email 最小化内容、链接过期/重放/错误联系人。
- 同意撤销、范围缩小、人员切换隔离、角色越权、2FA 未完成、到期数据删除。

## 12. 非目标

- 医疗诊断、治疗或用药建议。
- 自动呼叫紧急服务和电话外呼。
- 连续视频上传、实时远程视频查看、浴室视觉监测。
- 本版本内完整的机构多租户、EHR 集成、支付或移动端应用。

## 13. 当前代码迁移约束

- 保留现有 v3 资料上传、异步 assessment、规则决策、Kimi 回退、人员范围检查和本地样例模式；新增生产能力需通过显式 workspace mode 区分。
- 保留“上传历史视频不因片尾未见恢复而自动 Critical”的安全规则。
- 现有 demo/legacy 路由只可用于开发演示；生产客户端必须使用受版本化 schema 保护的 v3 或其后继 API。
- 在真实通知、身份、同意和数据删除尚未上线前，所有界面、邮件预览和文档必须继续明确标示 sample/simulated，避免与本 PRD 的 P0 目标混淆。
